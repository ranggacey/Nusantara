# Brief riset — 2026-11-04 10:29 WIB

Fokus rotasi run ini: PERFORMA (sudut yang terakhir dipakai
02:29 WIB; run sebelumnya: AUDIO 08:29, UX 06:29). Pertanyaan
riset: apa yang benar-benar bisa dihemat saat tab game tidak
terlihat, tanpa mengubah gameplay — dan apa yang sebenarnya
sudah ditangani browser sendiri sehingga tidak perlu diklaim
berlebihan?

Catatan konteks: loop render utama ada di
`src/components/Map3D.tsx` (satu `requestAnimationFrame` yang
menggambar seluruh desa 3D tiap frame). Poll data dunia di
`page.tsx` berjalan di server-side tick, bukan di loop render,
jadi jeda render TIDAK menghentikan jam game — saat kembali,
desa tetap di waktu server terbaru, bukan waktu yang tertinggal.

## Ringkasan riset (fakta dari sumber, bukan opini)

1. Spicy Yoghurt, "JavaScript Game Loop with Delta Time":
   browser menahan callback `requestAnimationFrame` di tab
   hidden, jadi loop memang sudah berhenti sendiri di tab
   tersembunyi — TETAPI sisa game tidak tahu itu: musik tetap
   jalan, hitungan berbasis jam terus jalan, dan saat kembali
   delta time bisa melonjak. Obatnya Page Visibility API:
   `visibilitychange` -> hidden = `pauseGame()` (hentikan loop
   dengan `cancelAnimationFrame`), visible = `resumeGame()`
   (mulai lagi, dan frame pertama hanya mengingat timestamp-nya
   — persis untuk mencegah lompatan dt).
   Tautan: https://spicyyoghurt.com/tutorials/html5-javascript-game-development/create-a-proper-game-loop-with-requestanimationframe

2. Codrops/Tympanus, "Building Efficient Three.js Scenes":
   untuk mencegah aplikasi terus merender saat tidak terlihat
   di layar, sesuaikan `frameloop` secara dinamis: saat
   `visibilitychange` dan `document.hidden`, set frameloop ke
   'never'; saat kembali, ke 'always' — lengkap dengan
   melepas listener saat cleanup. Alasan yang sama: browser
   membatasi sumber daya tab tak aktif setelah beberapa detik,
   jadi frame yang tertunda bisa menumpuk dan bikin
   tersendat saat kembali.
   Tautan: https://tympanus.net/codrops/2025/02/11/building-efficient-three-js-scenes-optimize-performance-while-maintaining-quality/

3. Reintech, "Applying the cancelAnimationFrame() Method":
   pola yang sama tanpa framework: simpan id animasi,
   `visibilitychange` -> hidden = cancel + id diset null,
   visible = mulai lagi hanya bila id null (supaya tidak ada
   dua loop berjalan bersamaan). Tanpa cancel eksplisit,
   frame yang tidak dibatalkan tetap mengantre dan bisa
   menumpuk, menyebabkan stutter saat tab kembali fokus —
   terutama di HP.
   Tautan: https://reintech.io/blog/tutorial-applying-cancelanimationframe-method

## Ide konkret

### Ide 9 — Jeda loop render saat tab disembunyikan (DIPILIH untuk dibangun run ini)
Masalah pemain: tab game yang ditinggal terbuka terus
mengantre frame 3D — baterai HP terkuras dan saat kembali
bisa tersendat. Cara kerja: di `Map3D.tsx`, dengarkan
`visibilitychange`; hidden -> `cancelAnimationFrame(raf)`,
raf = 0; visible -> reset penanda waktu (`last`) lalu
`requestAnimationFrame(loop)` lagi, hanya bila tidak ada
loop berjalan (penjaga raf = 0 mencegah loop ganda).
Cleanup melepas listener. Dampak kecil-sedang (jujur:
browser modern sudah menahan RAF di tab hidden, jadi
penghematan tambahan ini kecil — nilainya ada di frame
basi yang dibatalkan eksplisit, pencegahan loop ganda,
dan reset timestamp anti-lompatan), usaha kecil, risiko
rendah karena tidak menyentuh sim atau data sama sekali.
Diukur dari: build hijau + tes penjaga statis; efek baterai
tidak bisa diukur dari sini dan TIDAK diklaim.

### Ide 17 — Jeda poll data saat tab hidden (backlog, belum dibangun)
Masalah pemain: poll `/api/world` dkk. tetap jalan (meski
di-throttle browser) saat tab tidak dilihat. Cara kerja:
di `page.tsx`, hentikan interval poll saat hidden, lanjutkan
saat visible dengan satu fetch segar. Dampak kecil, usaha
kecil-sedang; hati-hati: jam game server tetap jalan, jadi
saat kembali UI harus langsung fetch ulang, bukan menunggu
interval berikutnya.

## Ide yang TIDAK direkomendasikan + alasannya
- Menghentikan sim server saat tab hidden: sim itu dunia
  bersama — menghentikannya dari satu tab akan membekukan
  kampung untuk semua pengunjung lain.
- Mengklaim "hemat baterai X%" tanpa pengukuran perangkat:
  tidak ada alat ukur baterai di run ini; klaim seperti itu
  akan bohong.
- `IntersectionObserver` untuk kanvas fullscreen: kanvas
  selalu memenuhi viewport saat halaman dibuka, jadi sinyal
  ini tidak menambah apa-apa dibanding `visibilitychange`
  untuk kasus ini.
