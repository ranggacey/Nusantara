## Ringkasan riset (fakta dari sumber, bukan opini)

1. Mobitoss, "HTML5 Games on Phones: Performance Checklist"
   (31 Okt 2026): muat hanya yang dibutuhkan layar pertama,
   sisanya dimuat sambil pemain membaca/bermain; tampilkan
   progres muat yang bergerak, bukan layar kosong; jaga frame
   rate STABIL (lebih penting daripada tinggi); jangan alokasi
   objek tiap frame (pakai object pooling) karena jeda garbage
   collection terasa sebagai patah-patah; gambar lebih sedikit
   (lewati yang di luar layar, cache latar statis); hemat efek
   (partikel, bayangan, blur mahal di HP); hentikan loop saat
   halaman disembunyikan (Page Visibility API); dan uji di HP
   menengah lama, bukan flagship.
   Tautan: https://www.mobitoss.com/guides/html5-games-on-phones.html

2. Playgama, "How to optimize 2D canvas and WebGL rendering
   for mobile browsers": batasi device pixel ratio ke 1-2
   (bukan 2,6-3 bawaan HP) karena GPU HP adalah bottleneck;
   kurangi draw call (gabung sprite ke satu atlas, urutkan
   per material); jangan buat buffer/objek baru di dalam
   render loop; untuk canvas 2D, gambar ulang hanya area yang
   berubah (dirty rect) bukan seluruh kanvas tiap frame; uji
   di HP menengah nyata, bukan DevTools desktop yang diperkecil.
   Tautan: https://playgama.com/blog/business-faqs/how-to-optimize-2d-canvas-and-webgl-rendering-for-mobile-bro/

3. Fakta silang dari ulasan Idle City Builder (AppBrain):
   pemain HP mengeluh game makin ngelag saat kota membesar
   dan meminta optimasi seperti "menyembunyikan bagian peta
   yang tidak terlihat" — artinya: culling objek di luar
   viewport adalah keluhan pemain nyata, bukan teori.
   Tautan: https://www.appbrain.com/app/idle-city-builder-tycoon-game/idle.city.builder

## Ide konkret untuk Nusantara

### Ide A — Layar muat yang jujur + tunda chunk 3D sampai siap (DIPILIH backlog)
- Masalah pemain: layar "Memuat Peta 3D..." lama tanpa kabar
  kemajuan terasa seperti macet; pemain bisa menutup tab.
- Cara kerja singkat: tunjukkan progres bertahap yang jujur
  (langkah muat: data dunia -> peta -> karakter), dan pisahkan
  chunk 3D dari paket awal supaya halaman ringan dulu tampil
  (kerangka + info kampung) sebelum kanvas berat dimuat.
- Dampak vs usaha: dampak sedang-tinggi (menjawab keluhan
  muat pertama yang sudah terobservasi), usaha sedang
  (dynamic import + skeleton; perlu uji build ukuran chunk).
  Ditunda dari run ini karena run ini mengambil irisan
  DESAIN-EKONOMI (panel kebutuhan, di bawah).

### Ide B — Cap DPR kanvas di HP (1,5-2) + culling objek luar viewport
- Masalah pemain: HP menengah ngelag saat desa ramai karena
  kanvas dirender di DPR penuh dan semua objek digambar.
- Cara kerja singkat: batasi pixel ratio renderer di HP dan
  lewati render objek yang sepenuhnya di luar viewport.
- Dampak vs usaha: dampak sedang, usaha kecil-sedang (satu
  tempat set pixel ratio; culling butuh uji visual agar tidak
  ada objek hilang di tepi layar). Masuk antrean performa.

### Ide C — Jeda loop render saat tab disembunyikan
- Masalah pemain: baterai terkuras dan HP panas saat tab
  ditinggal terbuka.
- Cara kerja singkat: Page Visibility API -> hentikan
  requestAnimationFrame saat hidden, lanjutkan saat kembali.
- Dampak vs usaha: dampak kecil-sedang, usaha kecil.
  Backlog murah untuk run performa berikutnya.

## TIDAK direkomendasikan
- Pindah engine ke WebGL murni / tulis ulang renderer: Playgama
  memang menyarankan WebGL untuk sprite banyak, tapi Nusantara
  sudah jalan di Three.js; rewrite merusak aturan "satu langkah
  kecil" dan berisiko regresi visual besar.
- Turunkan kualitas visual global (tekstur kecil semua, tanpa
  bayangan): mengorbankan identitas visual game demi performa
  yang belum terbukti jadi bottleneck; ukur dulu (ukuran chunk
  build, observasi HP) sebelum memotong kualitas.
