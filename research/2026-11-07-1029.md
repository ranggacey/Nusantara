## Ringkasan riset

1. "Next.js Dynamic Imports: Lazy Load Components & Cut Bundle
   Size (2026)" (StackNotice, DIBACA — ringkasan + cuplikan):
   - `next/dynamic` memisahkan komponen berat jadi chunk sendiri
     yang hanya diunduh saat komponen itu benar-benar dirender;
     `loading` menampilkan placeholder selama chunk diambil.
   - `ssr: false` mengeluarkan komponen dari HTML server — yang
     dilihat pengguna tanpa JS / koneksi lambat hanyalah placeholder.
   - Uji lakmus: bila aksi utama halaman bisa selesai tanpa
     komponen itu dirender, komponen itu kandidat lazy-load.
   - Ukur dampak lewat bundle analyzer (treemap) + Lighthouse
     (Total Blocking Time, TTI) — bukan perasaan.
   - Catatan jujur sumber ini: untuk icon library, tree-shaking
     pada static import sering lebih efisien daripada dynamic
     import — ukur dulu sebelum memindah.
   Sumber: https://stacknotice.com/blog/nextjs-dynamic-imports-lazy-loading-2026
2. "WebGL and Three.js: Building 3D Web Experiences That Actually
   Perform" (Simplified, DIBACA PENUH):
   - Draw call = bottleneck nomor satu WebGL; target <100/frame
     desktop, <50/frame HP. InstancedMesh = senjata utamanya
     (5.000 pohon = 1 draw call); mergeGeometries untuk statis.
   - Cap pixel ratio 2x (ponsel 3x = 9x piksel dibanding 1x, tanpa
     beda visual yang terasa); tanpa shadow map di HP (satu pass
     render ekstra bisa membelah frame rate); tekstur HP separuh
     resolusi desktop.
   - Lazy-load tekstur yang tidak langsung terlihat — first paint
     lebih penting daripada fidelitas lengkap.
   - Render loop: jangan render tiap frame bila tidak ada yang
     berubah (dirty flag); satu directional light berbayang
     maksimal (~3ms dari anggaran 16,67ms/frame).
   - Draco: GLB 10MB -> 500KB–2MB (decode CPU 50–200ms);
     three.js ~150KB gzipped; TTI target <3 detik.
   Sumber: https://simplified.media/guides/webgl-threejs
3. "Next.js Bundle Size Optimization: Reducing First Load JS by
   40%" (blog.nazrulkabir.com, cuplikan hasil cari):
   - Diagnosis dulu dengan @next/bundle-analyzer; strategi:
     code-split agresif via dynamic import; hasil kasus nyata:
     First Load JS ~501KB -> 120–306KB (turun ~40%), Lighthouse
     36 -> 73 pada contoh lain.
   - Patokan yang dipakai sumber-sumber ini: First Load JS hijau
     <200KB (gzip), merah bila membengkak dan merusak LCP.
   Sumber: https://blog.nazrulkabir.com/2026/01/nextjs-bundle-size-optimization-case-study/

## Ide konkret

### Ide 74 — Catat ukuran chunk tiap run sebagai angka performa
- Masalah pemain: klaim "lebih ringan" selama ini tanpa angka —
  observasi "muat pertama ~30–60 detik" vs "≤20 detik" tidak
  bisa dibandingkan karena cold start, koneksi, dan cache ikut
  bermain.
- Cara kerja: tiap run yang menyentuh build, catat di CHANGELOG
  ukuran 3 chunk terbesar + total `.next/static/chunks` dari
  build itu (perintah `du`/`find`, 1 menit). Bukan target
  absolut — tapi tren: chunk terbesar tidak boleh membengkak
  diam-diam antar rilis. Bila suatu hari angkanya naik >20%
  tanpa alasan, itu sinyal untuk Ide 75.
- Dampak vs usaha: kecil (sebagai disiplin ukur) / kecil.
  Penguat riset ini: StackNotice ("ukur dampak lewat bundle
  analyzer + Lighthouse, bukan perasaan") + nazrulkabir
  (diagnosis dulu, baru potong).

### Ide 75 — Dynamic-import modal berat yang jarang dibuka
- Masalah pemain: bila MusyawarahModal / TambahKarakter /
  RestoranInterior3D diimpor statis di page.tsx, kodenya ikut
  diunduh di muat pertama walau pemain tidak pernah membuka
  modal itu — persis pola "heavy component penalty" sumber
  StackNotice.
- Cara kerja: cek impor di page.tsx; pindahkan SATU modal dulu
  ke `next/dynamic` (dengan fallback loading yang jujur,
  mengikuti pola Map3D), ukur chunk sebelum/sesudah (Ide 74),
  pastikan modal tetap terbuka normal. Mulai dari satu modal,
  bukan semua sekaligus, supaya efeknya terukur.
- Dampak vs usaha: sedang / kecil-sedang. Penguat riset ini:
  StackNotice (uji lakmus: aksi utama bisa selesai tanpa
  komponen itu) + nazrulkabir (40% pada kasus nyata).
  Perhatian: modal yang dibuka dari banyak tempat butuh
  fallback yang sama; jangan dynamic-import komponen yang
  tampil di muat pertama (uji lakmus di atas).

### Ide 76 — Turunkan cap DPR ke 1,5 hanya bila angka live mendukung
- Masalah pemain: HP menengah ngelag saat desa ramai; cap DPR 2
  sudah ada (Ide 8) tapi Glitchless + Simplified sama-sama
  menyebut 1,5 sebagai angka yang lebih aman untuk HP lemah.
- Cara kerja: BUKAN dibangun sekarang — prasyaratnya angka
  baseline draw call/segitiga live (Ide 27) terbaca dulu +
  observasi jank di HP yang sama sebelum/sesudah. Bila angka
  live menunjukkan fill-rate (piksel) sebagai penyebab, bukan
  draw call, barulah cap diturunkan — dan label tetap dicek
  (teks 10px di DPR 1,5).
- Dampak vs usaha: kecil-sedang / kecil (bila prasyarat
  terpenuhi). Penguat riset ini: Glitchless (cap 1,5) +
  Simplified (ponsel 3x = 9x piksel). Bukan prioritas sebelum
  Ide 51/75.
